## 1. Своя нода

Официальные доки и снапшоты для 4663 существуют.

| Параметр | Значение |
|---|---|
| Софт | Nitro, тот же `nitro/v3.11.4-rc.3` что на публичном RPC, ArbOS 61 |
| Размер archive-path снапшота | **~0,954 ТБ** (срез 09-06), рост **+23 ГБ/сут** → на сегодня ≈ **1,16 ТБ** |
| Через год | ≈ 9,5 ТБ. Это главный аргумент против |
| Железо | Hetzner AX162-S (AMD EPYC, 2×3,84 ТБ NVMe) ≈ **€371/мес** |
| Флаги | `--execution.caching.archive=true --execution.caching.state-scheme=path` |
| Трейсы | `debug_traceBlockByNumber` с `flatCallTracer`. **`trace_block` не заработает никогда** — parity-style `arbtrace_*` существует только для pre-Nitro classic-блоков, которых у 4663 нет |
| Сеть строил | напрямую Offchain Labs, не RaaS |
| Ограничение | EIP-4844 блобы живут 4096 эпох ≈ **18 суток** — синк с нуля из L1 невозможен, только из снапшота |

**Вердикт по ноде: не поднимать.** €371/мес + 1,16 ТБ + обслуживание — дороже и медленнее,
чем Envio Pro ($480) или Chainstack Unlimited 100 RPS ($649), и на порядок дороже
единственного, что нам реально нужно сверх варианта A. Своя нода оправдана ровно одним:
если нужны **внутренние транзакции по всей истории** и при этом нельзя платить за трейс-провайдера.

## 5. На что хватает бесплатного варианта A

**Вариант A = только `eth_getLogs` по topic0 Transfer, публичный RPC, $0.**
Из `RECON.md`: 629 820 вызовов getLogs (span 100) + заголовки ≈ **1,26 млн RU**,
это укладывается в Chainstack Developer $0/3M RU, а на публичном RPC — **~18 часов** бэкфилла.

### Хватает полностью

| Возможность | Почему работает |
|---|---|
| **Весь граф ERC-20/721 переводов за всю историю** | 956 млн рёбер (from, to, token, amount, block, ts) — это ровно то, что даёт topic0-фильтр |
| **Все узлы и все рёбра для Flow-визуализации** | Etherscan Flow рисует именно переводы токенов, а не internal calls |
| **`GET /graph?address=…&depth=1..3`** | Вся BFS-обход поверх своей таблицы `transfers` |
| **`GET /path?from=&to=`** | Тот же граф |
| **Токены, символы, decimals** | `eth_call` + robinscan/`rhj/assets` бесплатно |
| **Метки адресов** | Etherscan V2 + growthepie + rhj/assets, всё $0 |
| **Хвост в реальном времени** | polling `eth_getLogs` раз в 1–2 с (блок 0,1 с → окно ~20 блоков), либо sequencer feed бесплатно |
| **Граф глубины 1 «на лету», вообще без бэкфилла** | измерено: фильтр по адресу, span 1M → **0,4 с**. Можно запускать сервис уже завтра |

### Не хватает — и это надо принять сознательно

| Чего нет | Последствие | Сколько стоит закрыть |
|---|---|---|
| **Internal transactions** (`debug_traceBlockByNumber` = -32601) | Не видно перемещений ETH внутри контрактных вызовов: мультисиг-выплаты, роутинг DEX, разделение средств через прокси. На Etherscan Flow это заметная часть картины | Chainstack Pro $199 + Unlimited $649, dRPC free (**не проверено**), Pinax, или своя нода €371/мес |
| **Нативные ETH-переводы** (не эмитят Transfer) | Простой перевод ETH между EOA в графе отсутствует. Нужен `eth_getBlockByNumber` по каждому блоку = **63 млн вызовов** вместо 630 тыс. | +$199–499 на Chainstack, либо Goldsky raw-датасет |
| **WebSocket-подписка** | Хвост только polling или sequencer feed | $0, но код другой, чем в плане Фазы 2 |
| **Хабы в запросах «на лету»** | span 100k на хабе → `exceeds limit`. Топ-контракты требуют предпосчёта | решается бэкфиллом, не деньгами |
| **Blockscout-метки** | закрыты Cloudflare | $0 — заменено Etherscan V2 + OLI |
| **18 часов на бэкфилл** и хрупкость публичного RPC | ~5 RPS, 429 на переполнение compute-бюджета батча | $70/мес Envio Starter сжимает это до часов |

### Прямой ответ

**Бесплатного варианта A хватает на весь заявленный продукт — интерактивный граф
движения средств по токенам.** Не хватает его на две вещи: **internal transactions**
и **нативные ETH-переводы**. Обе — расширение картины, а не её основа.

Самый дешёвый апгрейд на всю полноту: **Envio HyperSync Starter $70/мес** (снимает
боль бэкфилла) или **dRPC free** (210M CU с трейсом, если подтвердится).
Самый дорогой и худший — своя нода.

## 6. Проверка ключей Etherscan V2 на 4663 (2026-09-15, замерено)

Три ключа заполнены, все три валидны. Но главное — **не то, что ожидалось**.

### 6.1 Лимит — на IP, а не на ключ

| Конфигурация | 30 запросов | Успешных | Отбито лимитом | Реальная скорость |
|---|---|---|---|---|
| 1 ключ | 8,6 с | 23 | 7 | **2,7 req/s** |
| 3 ключа ротацией | 8,0 с | 23 | 7 | **2,9 req/s** |
| снова 1 ключ | 8,2 с | 22 | 8 | **2,7 req/s** |

Разница в пределах шума. Сообщение сервера: `Max calls per sec rate limit reached (3/sec)`.
**Ротация трёх ключей с одного IP не даёт ничего.** Ускорение возможно только разными
исходящими IP (прокси) — что уже нарушение ToS Etherscan, не рекомендую.

### 6.2 Etherscan V2 отдаёт на 4663 ровно то, чего не было в варианте A

| Эндпоинт | Результат | Значение для проекта |
|---|---|---|
| `account.tokentx` | **работает**, полные поля ERC-20 перевода | Рёбра графа по токенам, обе стороны сразу |
| `account.txlistinternal` | **работает, `value` != 0** | **INTERNAL TRANSACTIONS.** Поля: `from, to, value, type, traceId, isError`. Это главный пробел варианта A — закрыт бесплатно |
| `account.txlist` | **работает**, 4 из 5 tx с `value` != 0 | **Нативные ETH-переводы** — второй пробел варианта A, тоже закрыт |
| `contract.getsourcecode` | работает | verified-исходники + `ContractName` как метка |
| `contract.getcontractcreation` | работает | deployer + tx создания |
| `stats.tokensupply` | работает | totalSupply токена |
| `account.tokennfttx` | работает (у тестового EOA 0 записей) | ERC-721 рёбра |
| `account.addresstokenbalance` | **NOTOK** | портфель адреса недоступен, считать самим |

### 6.3 Лимиты пагинации (замерено)

- `offset` жёстко обрезается до **1000**, сколько ни проси.
- `page × offset ≤ 10 000`, дальше `Result window is too large`.
- **Обход:** окна по `startblock`/`endblock`, курсор по последнему блоку страницы. Работает.

Замеры на тестовом EOA `0xb2555cc4…23b8`:

| Что | Вызовов | Время | Результат |
|---|---|---|---|
| Все токен-рёбра за всю историю (`tokentx` окнами) | 17 | **9,6 с** | **16 317 рёбер** |
| Все internal за всю историю (`txlistinternal` окнами) | 4 | **1,7 с** | **3 055 записей** |
| Тот же адрес через сырой `eth_getLogs` (из п.0) | 64 | **229 с** | 6 333 ребра (только сторона `from`) |

**Etherscan быстрее сырого RPC в 24 раза и полнее** — отдаёт обе стороны плюс internal плюс нативные ETH.

Хабы: `tokentx` на топ-контракте с окном 500k блоков → `Query Timeout`;
окно 50k → 1000 записей за 8,0 с; окно 5k → 1000 записей за 1,2 с.
Хабы всё равно требуют предпосчёта, здесь ничего не изменилось.

### 6.4 Что это меняет в архитектуре

Вариант A перестал быть «граф только по токенам». Теперь бесплатно доступны все три типа рёбер:
ERC-20/721 (`tokentx`/`tokennfttx`), нативные ETH (`txlist`), internal ETH (`txlistinternal`).

Но у Etherscan другой профиль, чем у `eth_getLogs`:

| | `eth_getLogs` (публичный RPC) | Etherscan V2 |
|---|---|---|
| Режим | по диапазону блоков — **массовый бэкфилл** | по адресу — **точечный запрос** |
| Скорость | ~5 RPS, батчи | **2,7 req/s на IP, жёстко** |
| Пригодность для бэкфилла 956 млн рёбер | да, ~18 ч | **нет**, адресов 19,5 млн |
| Пригодность для «граф по адресу на лету» | средняя (хабы падают) | **отличная**, 10 с на адрес |
| Internal + нативный ETH | нет | **да** |

Вывод: это не замена ингесту, а **второй, дополняющий источник**. Правильная схема —
`eth_getLogs` (или HyperSync) для массового бэкфилла токен-рёбер, Etherscan V2 —
для обогащения конкретного адреса internal-переводами и метками по требованию.

## 7. Envio HyperSync на 4663 — замерено (2026-09-15)

Токен рабочий. Авторизация **только** `Authorization: Bearer <token>`; query-param и
`x-api-token` → 401. `GET /height` работает без токена, `GET /chain_id` → `{"chain_id":4663}`.

### 7.1 Пропускная способность

| Способ | Скорость | Полный бэкфилл (956 млн событий / 63,2 млн блоков) |
|---|---|---|
| Последовательно, 1 поток | 18,5k событий/с | ~14,4 ч |
| Сырой httpx, конкурентность 128 | **414k событий/с** | **~40 мин** |
| Потолок канала (без парсинга) | ~600k событий/с | ~27 мин |
| Официальный клиент `hypersync`, conc=32 | 41k событий/с | ~6,5 ч |

Официальный python-клиент **в 10 раз медленнее сырого httpx** — материализует Python-объекты
на каждый лог. Для бэкфилла не брать.

Rate limit: доведено до **512 одновременных запросов — ни одного 429**, заголовок
`x-ratelimit-cost: 0`. Упёрлись в свой канал (~20 МБ/с gzip), не в Envio.
⚠️ Free-тариф заявлен как fair-use; **суточная квота не проверена**, многочасовой нагрузки не было.

Размер страницы ограничен объёмом, не блоками: **45–53 тыс. логов на ответ**
(в разреженном начале цепи это 90k блоков, в плотной части — 1000–1400).
Полная выгрузка: **~32 ГБ** gzip на проводе / **~471 ГБ** распакованного JSON (492 Б/событие).

Arrow `/query/arrow-ipc` существует, но устойчивого выигрыша по объёму нет (−36 % на одном
диапазоне, +6 % на другом), и это не голый Arrow IPC, а свой конверт — `pyarrow` его не читает.
Смысла нет.

### 7.2 Какие таблицы доступны

| Таблица | Статус | Подтверждение |
|---|---|---|
| `logs` | **да**, полностью | 14 583 лога за 200 блоков |
| `transactions` | **да**, полностью | 7 670 tx за 581 блок |
| `blocks` | **да** (number, timestamp, hash, `l1_block_number`) | 2 298 заголовков за 1,31 с |
| **`traces`** | **НЕТ. 0 записей на всей цепи** | 4 независимых запроса, см. ниже |

**Трейсов на 4663 нет.** Схема трейсов сервером валидируется (подстановка несуществующего
поля даёт 400 со списком всех валидных имён), но таблица пуста:

- `"traces":[{}]` на диапазоне 5 110 блоков → 0
- то же от block 0 по всей цепи (next_block > archive_height) → 0
- на конкретном блоке 63 240 000, где лежит tx с `to` = контракт и `value` = 0,001 ETH,
  то есть заведомо порождающая `call`-трейс → **0**
- с фильтром по from/to: вся цепь пройдена за 2 запроса и 2,2 с → **0** (сервер не сканирует ничего)

Подтверждено доками: трейсы у Envio — платный add-on только для Base и Ethereum Mainnet.
HyperRPC `robinhood.rpc.hypersync.xyz` тем же токеном → **403 «Your token does not have
access to this product»** на всех методах, включая `eth_blockNumber`. Отдельная подписка.

### 7.3 Нативный ETH — top-level есть, internal нет

Статистика по 400 блокам: 10 520 tx, из них **1 145 с `value > 0`**;
220 чистых переводов (`input: 0x`), **925 (81 %) — вызовы контрактов с прикреплённым эфиром**.

Типы транзакций за ~10 000 блоков:

| type | кол-во | из них value>0 | что это |
|---|---|---|---|
| 2 | 65 434 | 15 113 | EIP-1559 |
| 0 | 46 305 | 2 586 | legacy |
| 106 (0x6A) | 5 047 | 0 | Arbitrum internal (системные) |
| 4 | 194 | 14 | EIP-7702 |
| 1 | 112 | 35 | EIP-2930 |
| **104 (0x68)** | 1 | 1 | **Arbitrum deposit — вход с L1, виден как обычная tx** |

Депозиты с L1 ловятся фильтром `{"type":[104]}` — вход средств в сеть виден **без трейсов**.
Вывод L2→L1 (сигнатура `L2ToL1Tx`) — **не проверено**.

### 7.4 `join_mode` — timestamp приезжает бесплатно

`join_mode: "Default"` автоматически подтягивает блок и транзакцию для каждого совпавшего лога.
Запрос только с `logs` вернул `{blocks: 20, transactions: 148, logs: 1394}` — **второй запрос
за таймстемпом не нужен**. Валидные значения: `Default`, `JoinAll`, `JoinNothing`.

### 7.5 Фильтрация по адресу

| Фильтр | Охват | Запросов | Время | Результат |
|---|---|---|---|---|
| `logs` по topic1 OR topic2 | **вся цепь** | 18 | **38,7–42,5 с** | 16 325 логов |
| `logs` по `address` | вся цепь | 2 | 3,7 с | 0 → адрес это EOA |
| `transactions` по from/to | вся цепь | **979** | **1 286 с (21,4 мин)** | **2 292 205 tx** — скан упирается в строки (~1 780 строк/с) |
| `traces` по from/to | вся цепь | 1 | <1 с | 0 |

**Вывод для ингеста: граф строить по `logs`.** `transactions` по адресу за полную историю
на хабах не масштабируется: у этого адреса **2,29 млн транзакций — 21,4 мин против 42 с по логам, разница в 30 раз**. Дёргать только точечно, по хешу или узкому окну.

Ловушка: **неизвестные ключи в селекторах молча игнорируются**. `{"kind":[...]}` не вызвал
ошибку и вернул всё подряд. Правильное имя — `type`. Также `max_num_logs` принимается,
но эффекта не даёт (с `max_num_logs:100` вернулось 16 960 логов).

### 7.6 Кросс-валидация корректности

Тот же EOA `0xb2555cc4…23b8`, независимые источники:

| Источник | Результат | Время |
|---|---|---|
| Etherscan V2 `tokentx` окнами | 16 317 рёбер | 9,6 с |
| HyperSync `logs` по topic1/topic2 | **16 325 логов** | 38,7 с |
| Сырой `eth_getLogs`, только сторона `from` | 6 333 ребра | 229 с |

Расхождение Etherscan vs HyperSync — **8 записей из 16 тыс. (0,05 %)**, вероятно ERC-721
(у Etherscan отдельный эндпоинт `tokennfttx`). Два независимых индексатора сходятся —
данным можно верить. На одном адресе Etherscan быстрее, на массовом бэкфилле HyperSync
вне конкуренции.

### 7.7 Покрытие целевой схемы ребра

| Поле | Откуда | Статус |
|---|---|---|
| `block_number`, `tx_hash`, `log_index`, `token_addr` | `log.*` | прямо |
| `timestamp` | `block.timestamp` (hex) | **в том же ответе** через `join_mode` |
| `from` / `to` | `log.topic1` / `topic2`, срез `[26:]` | да |
| `raw_amount` | `int(log.data, 16)` | проверено |
| `transfer_type` erc20 vs erc721 | наличие `topic3` (у ERC-20 ключ отсутствует) | да |
| **native ETH, top-level** | `transaction.value` + from/to/input/type | **да, отдельный тип ребра** |
| **native ETH, internal** | трейсы | **нет — единственная дыра** |
| `decimals`, `symbol` | не RPC, `eth_call` недоступен | добирать из robinscan / `rhj/assets` |
