## 0. Выбор инструмента (обоснование)

**Python 3.12 + httpx (async).** Причины:

- Разведка упирается не в CPU, а в round-trip и в rate limit публичной ноды. Go дал бы выигрыш в парсинге JSON, но фактический потолок — 50–70 req/s со стороны сервера, а не клиента. На этой скорости Python не является узким местом.
- `httpx` — единственная добавленная зависимость. Стандартный `urllib` не умеет HTTP/2 keep-alive пул и async, а `requests` синхронный. Альтернатива `aiohttp` не даёт ничего сверх.
- Агрегация 622k событий целиком помещается в память (`Counter`/`defaultdict`), отдельное хранилище на этапе разведки не нужно.

Для Фазы 2 вывод другой — см. раздел 8.

### Мост (п. 16)

Найден через `l1Address()` / `l2Gateway()` на токенах:

- **Канонический L2-гейтвей: `0x1d187c3e2da52d72bc9c41e3aba0fdfa6a7bf055`**
- WETH `0x0bd7d3…ad73` имеет `l1Address()` = `0xc02aaa39b223fe8d0a0e5c4f27ead9083c756cc2` — это **WETH Ethereum mainnet**. То есть WETH здесь — мостовой токен со стандартным Arbitrum-гейтвеем.
- **Stock Tokens (NVDA, AAPL, TSLA, AMZN, GOOGL, SPY, MRNA, USO, SPCX) не отвечают на `l1Address()`** → они выпускаются нативно на L2, через мост не идут.
- USDG тоже не мостовой, у него `owner()` = `0xcfa0388f5ddf905fdc08c45c716c15dc10a14c6f` (эмитент).

**Доля потоков через мост: 2 транзакции из 7 453 = 0,027 %** (типы `0x69` submit-retryable и `0x68` retry). Системные контракты Arbitrum (`0x…0064` ArbSys, `0x…006e` ArbRetryableTx, `0x…0066` ArbGasInfo) на цепи присутствуют, но их код — заглушка в 1 байт (precompile), логов они не эмитят.

Вывод по мосту: **трафик почти полностью внутренний.** Для flow-графа это скорее хорошо — активность не сводится к «завёл/вывел», внутри сети реально что-то происходит.

## 4. Поддержка методов RPC

### Трейсы — НЕ поддерживаются (п. 17)

| Метод | Ответ |
|---|---|
| `debug_traceBlockByNumber` | `-32601: the method does not exist/is not available` |
| `debug_traceTransaction` | `-32601: the method does not exist/is not available` |
| `trace_block` | `-32601: the method does not exist/is not available` |

**Зафиксировано: для internal transactions публичный RPC непригоден, нужен платный archive-провайдер.**

### Дополнительно: нода не архивная по состоянию

`eth_getBalance` на исторических высотах падает с `-32000: metadata is not found, <block>`:

| Глубина от головы | Результат |
|---|---|
| 0 / 100 блоков | иногда ok, нестабильно |
| 1 000 (≈ 100 секунд назад) | **ошибка** |
| 10 000 / 100 000 / 1 млн / 10 млн | **ошибка** |

То есть исторические балансы получить нельзя вообще. Логи при этом читаются с любой глубины (проверено на блоках ~1 млн и ~6 млн). Практический вывод: **балансы придётся реконструировать из потока Transfer**, а не запрашивать у ноды.

### Rate limit (п. 18)

Замер: N параллельных запросов подряд, наращивание до первых 429.

| Целевая конкурентность | Успешных / всего | Достигнутый RPS | 429 |
|---|---|---|---|
| 5 | 15/15 | 2,2 | — |
| 10 | 30/30 | 5,6 | — |
| 20 | 60/60 | 12,3 | — |
| 40 | 120/120 | 24,6 | — |
| 80 | 240/240 | 50,5 | — |
| 160 | 367/480 | 71,3 | **113 ответов 429** |

**Потолок ≈ 70–75 req/s, безопасный рабочий режим ≈ 50 req/s.** Отдельно: `Retry-After` в ответах не приходит, восстановление после 429 мгновенное (проверено — через 10 с запросы снова проходят).

### Лимит на размер батча — это бюджет по «весу», а не по количеству

Отдельная находка, которой не было в задании, но она критична для ингеста:

| Метод | Макс. вызовов в одном HTTP-батче |
|---|---|
| `eth_blockNumber` | 200 ok, 500 → 429 |
| `eth_getBlockByNumber` | 100 ok, 200 → 429 |
| `eth_call` | 50 ok, 100 → 429 |

Сервер считает не число элементов батча, а суммарную стоимость. **Безопасный размер батча: 50 вызовов для тяжёлых методов, 100 для чтения блоков.** Превышение возвращает 429 на весь батч целиком (не частично).

### Максимальный диапазон `eth_getLogs` (п. 19)

Ограничение — **по числу результатов, а не по ширине диапазона**:

| Проба | Результат |
|---|---|
| span 1 / 10 / 100 блоков | ok (26 / 425 / 4 137 логов) |
| span 1 000 блоков | ok, **42 400 логов** возвращено |
| span 1 000 (другой прогон) | `logs matched by query exceeds limit of **50000**` |
| span 1 200 / 1 500 / 1 800 / 2 000 / 3 000 / 5 000 / 10 000 | `exceeds limit of **10000**` |
| span 10 000 / 100 000 / 1 000 000 с фильтром по одному адресу | `exceeds limit of 10000` |

Два разных значения лимита в сообщениях (**10 000 и 50 000**) означают, что за балансировщиком стоят ноды с разной конфигурацией. **Планировать надо по худшему: 10 000 логов на запрос.**

При средней плотности 15,18 Transfer/блок это даёт ~658 блоков на запрос; в плотных регионах цепи замерено до 28 логов/блок → ~357 блоков. Плюс на 3 из 60 окон по 1 000 блоков пришёл `-32000: log query timed out`.

**Рабочее окно: 300 блоков с адаптивным сжатием при ошибке.**

**973 блока/с при конкурентности 4** → полный бэкфилл цепи за **≈ 18 часов** на бесплатном RPC.

### Ловушка: `blockTimestamp` в логах всегда `0x0`

Объекты логов содержат поле `blockTimestamp`, но оно **всегда равно `0x0`** — проверено на блоках 1 млн, 20 млн, 50 млн и на голове. Полагаться на него нельзя, timestamp придётся добирать отдельно заголовками блоков. Это добавляет вызовов в смету (учтено в разделе 7).

## 5. Blockscout закрыт Cloudflare

Все три сценария считаются на **62 981 835 блоков** и **≈ 956 млн Transfer-событий** *(оценка)*.

Тарифы Chainstack: 1 RU за обычный вызов, 2 RU за archive-вызов. Планы: Developer $0 / 3M RU, Growth $49 / 20M, Pro $199 / 80M, Business $499 / 200M. Unlimited Node add-on: $149 за 25 RPS, $649 за 100 RPS (плоская плата).

| **Итого** | | **629 820** |

- **RU: 629 820 × 2 = 1,26 млн RU.**
- **Влезает в бесплатный Developer ($0 / 3M RU) с запасом в 2,4 раза.**

**Оптимальный путь для B: Unlimited 100 RPS ($649) на неделю бэкфилла, затем даунгрейд на 25 RPS ($149/мес).** Это дешевле и быстрее, чем $499 + $199/мес по RU.

### Сценарий C — A + трейсы только на блоках с транзакциями к контрактам

**Замерено: блоков, содержащих хотя бы одну транзакцию к контракту — 600 из 600 = 100,0 %.**

**Следовательно C ≡ B. Экономия ровно нулевая.** Фильтр «блок содержит tx к контракту» на этой сети не отсекает ничего: при 11,4 пользовательских транзакциях на блок и 91,45 % транзакций, направленных в контракты, вероятность блока без единой контрактной транзакции пренебрежимо мала.

Сценарий C как способ сэкономить на этой конкретной сети **не существует**. Если нужен промежуточный вариант — фильтровать надо по другому признаку (например, трейсить только блоки, где есть tx с `value > 0` к EOA — это 27,65 % транзакций), но это уже не C из задания, и такой фильтр теряет главное, ради чего трейсы и нужны: internal-переводы, инициированные контрактами.

## 8. Выводы

### Есть ли в сети органическая активность?

**Да. Однозначно.** Граф не вырожденный, и вот на чём этот вывод держится:

1. **Концентрация 29,4 % на топ-5**, а не 90 %+. Порог вырожденности из задания не достигнут с большим запасом.
2. **101 467 уникальных адресов** и **174 325 уникальных рёбер** — в сэмпле, покрывающем 0,065 % цепи.
3. **6 523 адреса с входящей И исходящей степенью > 1** — узлы, ради которых flow-граф и существует, в одном лишь сэмпле.
4. **16,6 % адресов возвращаются в окнах, разнесённых на сутки-двое.** Это живые кошельки, а не одноразовые адреса спам-рассылки.
5. **9 079 уникальных токен-контрактов**, из них 1 553 активны в нескольких далеко отстоящих окнах.
6. В верхушке отправителей транзакций — **EOA с нулевым кодом**, максимум 30 tx на адрес. Трафик распределённый.
7. На сети живёт **настоящая DEX-инфраструктура**: пулы Uniswap V3 (`slot0`/`fee`/`token0`/`token1`), периферия V4 (`poolManager`), роутер V2-типа. Это генерирует именно многохоповые потоки, которые интересно рисовать.
8. **Мостовой трафик — 0,027 %.** Активность внутренняя, а не «завёл-вывел». Для flow-графа это лучший из возможных раскладов.

Честные оговорки, которые нужно держать в голове:

- **65,3 % адресов в сэмпле имеют степень ≤ 1.** Это артефакт короткого окна (1 000 блоков ≈ 100 секунд), при полной индексации степени вырастут, но часть адресов действительно одноразовая.
- **21,9 % всех Transfer касаются нулевого адреса** (15,0 % mint + 6,9 % burn), и львиная доля из них — техническое wrap/unwrap WETH. Эти рёбра нужно помечать отдельным типом и по умолчанию скрывать, иначе граф утонет в них.
- **WETH даёт 36,7 % всех событий.** Без фильтра по токену граф на любом активном адресе будет наполовину состоять из WETH-переливов.
- Экстраполяции в 782 млн транзакций и 956 млн Transfer сделаны по сэмплу 600 блоков / 41 000 блоков соответственно. Порядок величины надёжен, точность ±20 % не гарантирую.

### Какой сценарий брать

**Рекомендация: сценарий A. Однозначно.**

1. **C не существует** как способ сэкономить — 100 % блоков содержат контрактные транзакции, фильтр не отсекает ничего. Выбор реально стоит между A и B.
2. **B стоит в 101 раз больше вызовов ради маргинального прироста рёбер.** Поток ценности на этой сети — токенный: 956 млн Transfer против 782 млн транзакций, 91,45 % транзакций уходят в контракты. Граф движения средств здесь — это граф ERC-20, а не граф нативного ETH.
3. **A влезает в бесплатный тариф.** 1,26 млн RU против квоты в 3 млн. Поддержание хвоста — 516 тыс. RU/мес, тоже бесплатно. B требует платного архивного провайдера **до того, как на экране появится первое ребро**: трейсы на публичном RPC не отвечают в принципе.
4. **A даёт полный бэкфилл за 18 часов на бесплатной публичной ноде** — замерено, не оценка. B — от недели до месяца и от $649.

Что теряем, отказавшись от трейсов: internal-переводы нативного ETH, инициированные контрактами (сплиттеры, мультисенды, возвраты из роутеров). На сети, где нативный газ — ETH, а стоимость движется в ERC-20, это заметная, но не критичная потеря.

> ⚠️ **Разделы 1–8 отражают картину «только публичный RPC».** После их написания
> найдены источники, которые меняют экономику и частично закрывают потерю трейсов.
> Итоговая рекомендация — в **разделе 9**, он имеет приоритет над выводами выше.
> Полная раскладка по всем вариантам — в `OPTIONS.md`.

**Предлагаемый путь:** строить на A, а нативные ETH-переводы уровня транзакции (не internal) добрать **опционально, позже**, из `eth_getBlockByNumber` — там есть `to`, `from`, `value`, и трейсы для этого не нужны. Цена вопроса: 62,98 млн вызовов батчами по 100 = 630 тыс. HTTP-запросов, ~126 млн RU. Это отдельное решение, к которому имеет смысл вернуться **только если после запуска A выяснится, что пользователям не хватает именно ETH-рёбер**. Сейчас закладываться на это не стоит.

### Про выбор стека для Фазы 2

Разведка показала, что узкое место ингеста — не CPU и не парсинг, а **rate limit провайдера (50 req/s) и лимит в 10 000 логов на запрос**. ## 9. Обновление после разведки альтернативных источников (2026-09-15)

Разделы 1–8 исходили из того, что единственный доступный источник — публичный RPC.
Это оказалось неверно. Ниже — что изменилось. Все числа замерены, не оценены.
Подробности и полный обзор вариантов — в `OPTIONS.md`.

### 9.1 Экстраполяции подтвердились независимо

`robinscan.io/api/stats` отдаёт реальные тоталы сети без Cloudflare и без ключа:
**726 454 429 транзакций, 19 466 382 адреса, 1 879 397 токенов** на блоке 63 230 905.

| | Моя экстраполяция по 600 блокам | Реальное (в пересчёте на ту же высоту) | Ошибка |
|---|---|---|---|
| Всего транзакций | 782 339 360 | 723 592 885 | **+8,1 %** |

Заявленная в разделе 8 точность «±20 % не гарантирую» оказалась консервативной.
Оценку в **956 млн Transfer** после этого можно считать надёжной в тех же пределах.

### 9.2 Экономика сценария A изменилась: 40 минут вместо 18 часов

**Envio HyperSync** поддерживает сеть 4663 первым классом (`robinhood.hypersync.xyz`),
free-тариф требует только бесплатной регистрации.

| Способ бэкфилла 956 млн Transfer | Скорость | Время |
|---|---|---|
| Публичный RPC, `eth_getLogs` (раздел 7) | ~5 RPS | 18 ч |
| HyperSync, официальный python-клиент, conc=32 | 41k событий/с | 6,5 ч |
| **HyperSync, сырой httpx, conc=128** | **414k событий/с** | **~40 мин** |

Rate limit не нащупан до **512 одновременных запросов** (ни одного 429,
заголовок `x-ratelimit-cost: 0`) — упёрлись в собственный канал.
⚠️ Суточная квота fair-use **не проверена**, многочасовой нагрузки не было.

Объём: ~32 ГБ gzip на проводе / ~471 ГБ распакованного JSON (492 Б на событие).
Официальный клиент брать не надо — он в 10 раз медленнее сырого httpx.

`join_mode: "Default"` подтягивает блок и транзакцию к каждому логу, поэтому
**таймстемп приезжает в том же ответе** — отдельный запрос за заголовками,
заложенный в расчёт раздела 7, не нужен вовсе.

### 9.3 Трейсы: вывод раздела 4 подтверждён и расширен

`debug_traceBlockByNumber` отсутствует не только на публичном RPC:

| Источник | Трейсы на 4663 |
|---|---|
| Публичный RPC | нет (-32601) |
| `robinhood-rpc.publicnode.com` | нет, и `eth_getLogs` там вообще 403 |
| Alchemy | нет Debug/Trace API на этой сети |
| **HyperSync** | **нет — 0 записей**, подтверждено 5 независимыми запросами |
| HyperRPC | 403, отдельная платная подписка |

У HyperSync схема трейсов валидируется сервером, но таблица пуста: запрос на
конкретном блоке с транзакцией `to` = контракт и `value` = 0,001 ETH, заведомо
порождающей `call`-трейс, вернул ноль. По докам Envio трейсы — платный add-on
только для Base и Ethereum Mainnet.

**`trace_block` на этой сети не заработает никогда:** parity-style `arbtrace_*`
существует только для pre-Nitro classic-блоков, которых у чейна 4663 нет.

### 9.4 Потеря трейсов закрывается частично и с другой стороны

**Etherscan V2 поддерживает chainid 4663** (эксплорер `robin.etherscan.io`) и отдаёт
по обычному бесплатному ключу то, чего нет ни на одном RPC:

| Эндпоинт | Что даёт |
|---|---|
| `account.txlistinternal` | **internal transactions с `value != 0`** — та самая потеря из раздела 8 |
| `account.txlist` | нативные ETH-переводы top-level |
| `account.tokentx` | рёбра ERC-20, обе стороны сразу |
| `contract.getsourcecode` | verified-исходники и имя контракта как метка |

Ограничения замерены: `offset` режется до 1000, `page × offset ≤ 10 000`
(`Result window is too large`), обход — окна по `startblock`/`endblock`.
**Лимит привязан к IP, а не к ключу:** один ключ и три ключа ротацией дали
одинаковые 2,7 req/s. Масштабируется только числом исходящих IP.

Это не замена ингесту (19,5 млн адресов при 2,7 req/s), а **источник по запросу
для конкретного адреса**. Для Flow-графа этого достаточно: пользователь всегда
смотрит на один адрес.

Нативный ETH top-level дополнительно приходит из HyperSync `transactions`,
включая зачисления с L1 (тип `104`, ловятся фильтром `{"type":[104]}`).
Из транзакций с `value > 0` **81 % — вызовы контрактов**, то есть без трейсов
видно вход эфира в контракт, но не его дальнейший путь.

### 9.5 Кросс-валидация данных

Один и тот же EOA `0xb2555cc4…23b8`, три независимых источника:

|---|---|---|

| Нативный ETH + вход с L1 | HyperSync `transactions` | $0, тот же поток |
| Таймстемпы | `join_mode: "Default"` | $0, в том же ответе |
| Internal ETH по адресу | Etherscan `txlistinternal` | $0, 2,7 req/s на IP |
| Метки, verified, символы | Etherscan + growthepie + rhj/assets + robinscan | $0 |
| Хвост | polling `eth_getLogs` / sequencer feed | $0 |

**Весь продукт собирается за $0.** Публичный RPC при этом остаётся нужен только
для хвоста и точечных `eth_call` — основным источником он больше не является.

Сценарий B (полные трейсы по всей истории) **по-прежнему недоступен ни за какие
разумные деньги на бесплатных источниках** и требует либо платного архивного
провайдера с debug API, либо своей ноды (~1,16 ТБ, +23 ГБ/сут, ~€371/мес).
Учитывая, что internal-переводы теперь доступны по запросу для конкретного адреса,
необходимость в B отпала для продукта и осталась только для аналитики по всей сети.
